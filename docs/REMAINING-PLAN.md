## 4. 目标架构

```text
人工界面 ───────────────┐
                        ├─> 统一能力网关 ─> Core/事务 ─> SQLite
页内 AI 管家 ─> 工具循环 ┤       │
                        │       ├─ 身份、scope、确认票、幂等
外部 Agent ─> MCP+Skill ┘       └─ 审计、错误码、结果来源
```

必须满足四条原则：

1. 数据库是唯一事实源；模型记忆和提示词都不是事实源。
2. REST、MCP、页内管家不得各自实现一套业务规则，全部走同一能力网关。
3. Agent 没有隐藏权限；普通写入受 scope 控制，高风险操作只能由人工界面批准。
4. 管家的每个事实和修改都能追溯到工具调用与具体数据记录。

## 7. R1：钥匙底座——统一能力网关与权限

### R1.1 建立统一工具目录

为每个可供 AI 使用的能力登记以下信息：

- 稳定工具名和版本；
- 输入/输出 schema；
- 所属数据域；
- 所需 scope；
- 只读、普通写入或高风险操作；
- 是否要求幂等键；
- 审计摘要和禁止记录的敏感字段。

REST、MCP 和页内管家都从该目录注册或调用工具，不再维护三份手写映射。

- 人工界面的 REST 路由调用网关中的同一业务命令；
- 页内管家在服务进程内调用工具目录，不经模型可控 URL 拼接；
- MCP 只通过专用 Agent 工具入口调用目录中的已登记工具，不再转发任意业务 REST 路径。

### R1.2 真正校验 Agent token

当前 MCP 会发送 Bearer token，但服务端只据此把 actor 标成 `agent`，并未验证 token。需要完成：

- 对 token 做哈希匹配和恒定时间比较；
- 拒绝缺失、无效、过期或已撤销 token；
- 执行 `api_tokens.scopes_json`，不能只保存不使用；
- 每次成功使用更新 `last_used_at`；
- 审计记录准确的 token id、Agent 名称、工具名和结果；
- token 原文只在创建时显示一次，数据库只保存 hash。

scope 采用按域读写：`tasks:read`、`tasks:write`、`projects:read` 等。界面只提供容易理解的预设：只读、任务/项目、财务/健康、全部普通能力。

### R1.3 分开“人”和“Agent”

- 桌面版启动时生成内存级 UI 会话，人工界面使用受保护会话访问高风险确认接口。
- MCP 请求进入独立的 Agent 工具入口并强制使用 Agent token；它不能改为访问无 token 的 UI 路由来伪装成人工界面。
- `/confirmations/:id/approve`、恢复备份、清理历史、token 管理等接口只接受 UI 会话。
- 即便错误授予了过宽 scope，MCP 工具层仍不暴露“批准确认票”。
- 开发模式允许显式的 localhost 调试会话，但不得成为生产默认后门。

### R1.4 token 与密钥管理界面

在设置页增加“AI 接入”区域。这是完成“钥匙”所需的唯一界面加法，不新增侧栏页面，也不改动现有业务数据库界面：

- 查看 token 名称、权限、创建时间、最近使用和是否撤销；
- 创建、复制一次、撤销和轮换 token；
- 一键复制 MCP 连接配置，不要求用户手工寻找 `mcp-token.txt`；
- 旧开发 token 提供迁移和轮换，不静默使现有 Agent 失效。

LLM API Key 与 Agent token 概念分开。LLM Key 后续改用 Windows 凭据保护/DPAPI；迁移成功前保留回滚，任何日志、数据库和导出都不能出现明文。

### R1.5 收紧批量执行

- 废弃“任意 REST 路径”的 `batch_run`。
- 批量项只能引用统一工具目录中的工具名，并逐项校验 schema 和 scope。
- 一批最多 20 项；使用同一个幂等键；遇到高风险项只创建一张摘要清楚的确认票，不执行半批数据。
- 禁止路径拼接绕过、禁止确认批准、禁止物理删除和 schema 操作。

### R1 验收

- 无 token、伪造 token、撤销 token访问 Agent 接口均为 401。
- 只读 token 写入时为 403；跨域 token 不能访问未授权数据。
- Agent 无法批准确认票，也无法通过 `batch_run` 绕过。
- 审计能回答“哪个 Agent 在何时用哪个工具改了哪条数据”。
- 数据库、日志、导出中找不到 token 或 API Key 明文。

## 8. R2：MCP 与 Skill 完整化

### R2.1 MCP 工具补齐原则

只暴露已经存在的业务能力，不借机新增数据库字段。优先补齐：

- 任务：列表、详情、创建、更新、周期规则查看与检查；
- 项目：列表、详情、资料区、普通更新；
- 想法：列表、创建、更新；升级任务仍走确认票；
- 财务：支出/收入/账户流水的查询与普通登记、分类字典、汇总；
- 健康：单日、区间查询和当日更新；
- 复盘：列表、详情、草稿创建与更新；
- 系统：today、能力清单、连接状态、待确认摘要。

永久删除、备份恢复、确认批准和 schema 变更不作为普通 MCP 工具开放。想法升级、归档或恢复若需要让 Agent 发起，只能暴露“申请”工具：工具只创建确认票，不直接执行。

### R2.2 统一响应和错误

所有工具返回：

- `ok`；
- `data`；
- `meta.request_id`、`actor`、`tool`、`schema_version`；
- 失败时使用稳定错误码：验证失败、未找到、版本冲突、权限不足、需要确认、重复请求、服务不可用。

模型不能从错误堆栈猜数据。服务端也不能把本机路径、Key 或 SQL 直接返回给 Agent。

### R2.3 MCP 资源

至少提供：

- `paios://today`
- `paios://schema/overview`
- `paios://projects/{id}`
- `paios://finance/summary`
- `paios://workflow/active`

资源只读，并注明生成时间、时区和数据范围，防止 Agent 把旧结果当作当前结果。

### R2.4 Skill 重写

把 `skills/paios/SKILL.md` 改为精简入口，详细规则拆到 references：

- 先读后写和“不知道就说不知道”；
- 任务/周期任务规则；
- 项目策划流程；
- 财务分类、整数分和账户流水规则；
- 健康、复盘和本地日期规则；
- 确认票、高风险和权限失败的处理；
- 常见 Agent 的连接示例。

删除已过时内容，例如把运动字段写成 `cloud_content`，以及“页内管家永远不调用工具”的旧结论。

### R2.5 契约与兼容测试

- 启动真实 stdio MCP，执行 initialize、list tools、read resource、读写各一条测试数据。
- 用只读 token、写 token、撤销 token分别测试。
- 对工具名称、schema 和错误码做快照；破坏性改名必须升契约版本。
- 对每个写工具验证审计、幂等和权限。

### R2 验收

- 一个新接入的兼容 Agent 只凭复制的配置和 Skill，就能读取真实任务、项目、财务、健康和复盘。
- Agent 可以执行被授权的普通写入，但不能越权或批准高风险操作。
- 同一输入重复发送不会生成重复财务记录或重复任务。
- MCP 文档、Skill 和实际 `list tools` 一致。

## 9. R3：AI 管家只读工具闭环

这一阶段先只读，目的是先解决“回答来自真实数据”这一核心问题，不急着让模型改库。

### R3.1 替换整库摘要提示词

- 删除当前 `localButlerFacts` 把最多 200 条任务、100 个项目、100 条想法和当日健康一次塞进提示词的方式。
- 系统提示词只保留身份、规则、当前日期和可用工具说明。
- 模型根据问题请求工具；服务端验证并执行；把工具结果返回模型；最多循环 8 轮、20 次调用。
- 最终回答必须基于本轮工具结果。没查到就明确说“本地没有查到”，不得用模型常识补造个人数据。

### R3.2 只读来源轨迹

每条回答保存并展示可折叠的来源摘要，例如：

- 已读取任务 12 条；
- 已读取 8 月 1 日至 8 月 30 日支出；
- 使用项目 `xxx` 的工作区资料；
- 某个工具失败或数据为空。

来源轨迹保存工具名、参数摘要、记录 id 和结果状态，不保存 Key、完整图片或无必要的长文本副本。

### R3.3 上下文控制

- 默认只带最近必要的对话，长历史先做本地摘要；摘要不能替代工具查询。
- 工具返回分页和字段选择，避免一次把全部数据库送给模型。
- 单轮设置超时、最大工具次数和最大返回大小；超限时给用户明确提示。
- 临时网络错误最多自动重试一次，权限/验证错误不重试。

### R3.4 只读问题验收集

用固定数据库和 mock LLM 覆盖：

1. “我最早到期的任务是什么？”必须返回真实排序结果。
2. “打开某任务的正文说了什么？”必须读取该任务详情，不能把备忘当正文。
3. “本周花了多少钱？”必须调用财务查询并给出可核对金额。
4. “今天睡了多久？”必须读取健康记录；缺失时回答未知。
5. “不存在的项目进度如何？”必须回答未查到。

### R3 验收

- 上述问题连续多次回答都与数据库一致。
- 管家回答中能看到使用了哪些本地数据来源。
- 数据读取失败时不输出看似确定的答案。
- 第一条用户消息先出现在界面，再显示加载状态；失败后该消息仍保留并可重试。

## 10. R4：AI 管家受控写入、确认与图片

### R4.1 普通写入

- 只有用户消息明确表达修改意图时，才允许调用写工具。
- 写入全部走 R1 的统一能力网关，禁止管家直接 SQL 或调用无权限 REST。
- 普通创建、更新在用户已明确下令时不再多问一次；界面在执行过程中显示简短操作摘要，成功后回显真实记录和 id。
- 每轮对话生成幂等键；网络重试或用户重复点击不能重复落库。

第一批只支持现有普通操作：创建/更新任务、项目资料、想法、当日财务、当日健康和复盘草稿。永久删除、归档恢复、历史财务修改和确认批准不进入第一批。

### R4.2 高风险确认

- 工具判断为高风险时，只生成确认票并停止执行。
- 对话中展示“准备做什么、影响哪些记录、为什么需要确认”。
- 用户只能在人工确认卡片中批准或拒绝；模型不能代点，也不能通过后续工具调用批准。
- 批准后显示最终执行结果；过期、拒绝或冲突都要有明确状态。

### R4.3 图片真正送达模型

- 当前图片只保存到本机附件目录，后续请求只发送了文字。需要把本条消息中的图片按模型兼容格式传出。
- 保留 MIME、数量和大小限制；默认最多 4 张，每张限制在可控范围。
- 支持图片的模型发送 data URL 或兼容上传引用；不支持时在发送前明确提示，不能假装已经看图。
- 图片不进入 MCP 普通资源，不写进审计正文，不出现在数据导出中。

### R4.4 对话可靠性

- 明确区分“用户消息已保存”“模型正在回答”“工具正在执行”“等待人工确认”“失败可重试”。
- 支持取消本轮请求；取消不删除已经发送的用户消息。
- 模型回答失败时不留下半条 assistant 消息；已成功的工具写入必须在轨迹中说明，避免用户误以为全部回滚。
- 会话归档、恢复、复制继续保留。

### R4 验收

- “新增明天的任务 X”只生成一条真实任务，重试不重复。
- “把已存在任务的正文改为 Y”修改的是正文，不是备忘。
- “删除全部归档”不能被模型直接执行，只能进入受保护确认流程或明确拒绝。
- 图片问题使用真实图片输入；不支持图片的模型会在调用前提示。
- 每次写入都能从对话轨迹和审计日志追踪。

## 11. R5：外部 Agent 使用闭环

本阶段在 R2 完成后即可开始，可与 R3 并行。目标是让 Skill + MCP 真正成为通用钥匙，不在桌面程序里随意启动第三方命令或构建“多 Agent 群聊”。

### R5.1 接入流程

- 设置页选择权限预设并创建 Agent token。
- 一键复制对应 MCP 配置和 Skill 路径。
- 提供“测试连接”：检查服务、token、权限、工具版本和时区。
- 外部 Agent 连接后，设置页显示最近使用时间和最近工具调用。

### R5.2 分领域 Skill

在不新增业务功能的前提下，提供四个操作指南：

- 项目策划：读取项目资料，输出阶段方案，经用户确认后写项目资料或任务；
- 财务记录：先核对金额、日期和分类，再登记；
- 健康管理：只基于已有健康记录总结，缺失不猜；
- 复盘协作：读取事实、起草复盘，用户负责最终确认。

这些可以是一个 Skill 的分支 references，不要求安装四套程序。

### R5.3 边界

- Personal AI OS 只提供数据、工具、权限和审计，不负责自动安装或偷偷启动 Codex、Claude 等第三方 Agent。
- 第三方 Agent 的模型费用、登录和运行环境由用户自己决定。
- 若以后需要“由管家派单给多个 Agent 并跟踪状态”，必须另立计划并得到授权；当前不预建任务队列和 Agent 配置数据库。

### R5 验收

- 至少用一个外部兼容 Agent 完成：读项目 → 给方案 → 经用户同意写入项目资料或任务。
- 换成只读 token 后，同一 Agent 无法写入。
- 断开或撤销 token 后立即失效，不影响本机人工界面。

## 12. R6：稳定性、回归与单 EXE 交付

### R6.1 必补测试

- 周期任务启动补齐：跨月、跨年、闰日、重复启动、100 条以上先备份、部分失败后重试。
- token 与 scope：401/403、撤销、轮换、UI-only 确认、批量绕过。
- 管家工具循环：多轮 tool call、空结果、超时、模型格式错误、重复请求和部分成功。
- 财务：整数分、分类筛选、账户存入/取出、汇总不受普通支出账户假设影响。
- 任务详情：自动保存、长文本、正文与备忘分离、斜杠块删除。
- Web 最小端到端：九项导航、任务详情、管家第一条消息、设置保存、归档筛选删除。
- 备份恢复：升级前备份、损坏库拒绝、恢复失败保留原库。

### R6.2 运行诊断

- 服务启动失败时桌面窗口不能直接消失；显示可理解的错误和日志位置。
- 检查端口占用、资源缺失、数据库锁、迁移失败和 Node 子进程退出。
- 设置页提供只读诊断摘要与“复制诊断信息”，自动去除 token、Key 和对话正文。

### R6.3 真正的单 EXE

用户交付物只保留一个 `Personal-AI-OS.exe`：

- 把 Node 运行时、server bundle、SQLite 原生模块和图标作为版本化资源嵌入 EXE；
- 首次启动由程序自动校验并释放到 `%LOCALAPPDATA%` 的内部运行目录，用户不安装、不手动解压；
- 资源释放使用校验和、临时目录和原子替换，失败不留下半套运行时；
- 用户数据继续保存在 `%USERPROFILE%\.paios\`，升级运行时不能覆盖数据；
- 第二次启动复用已校验资源，避免每次解压；
- EXE 复制到另一台干净 Windows 机器后可直接双击运行，不依赖仓库、pnpm 或系统 Node。

### R6.4 最终发布门槛

- 全新 Windows 用户：只复制一个 EXE，双击后 10 秒内看到界面。
- 第二次双击聚焦已有窗口，不启动第二个数据库写者。
- 无网络时除 AI 回答外，其余数据库功能全部可用。
- 无 API Key 时管家清楚提示配置，不影响其它页面。
- 旧数据升级、备份、恢复、周期补齐和普通编辑全部通过回归。
- 发布包经过哈希记录，版本号能在设置/诊断中查看。

## 13. 明确延期，等待单独授权

以下内容不进入本轮实施：

- 周/月统计、长期数据精简和图表；
- 新的任务属性、健康指标、财务类别或复盘模板；
- 银行、微信/支付宝、日历或健康平台自动同步；
- 多用户、云同步、移动端；
- 投资持仓、习惯、饮食、心情数据库；
- 自动安装或编排多个第三方 Agent；
- 新一轮整体视觉重构。

## 14. 执行与暂停规则

实施主线按 R0 → R1 → R2 → R3 → R4 → R6 推进；R5 在 R2 后即可与 R3 并行，但必须在 R6 发布前验收。每个阶段都必须：

1. 先备份和写验收测试；
2. 只修改本阶段需要的范围；
3. 通过类型检查、自动测试和对应人工验收；
4. 更新 MCP/Skill/安全文档；
5. 发现需要新增业务表、属性、页面或外部服务时暂停，向用户说明并取得授权。

R1、R2 未完成前不得开放 AI 写入；R3 只读准确性未通过前不得进入 R4。

## 15. 审阅记录

审阅时间：2026-08-30。审阅结果：**通过，已根据发现修订**。

| 审阅发现 | 修订结果 |
| --- | --- |
| R2 已包含外部 Agent 验收，R5 又排在 R4 后，职责和顺序重复 | 将 R5 收敛为接入体验与分领域操作指南，改为 R2 后可与 R3 并行 |
| 初稿要求 MCP 带 token，但没有说明如何阻止 Agent 改走无 token 的 UI REST | 增加专用 Agent 工具入口；MCP 不能转发任意 REST；高风险 UI 路由要求独立 UI 会话 |
| “创建、更新前显示摘要”可能被理解为每次普通写入都再确认一次 | 改为明确下令后直接执行普通写入，仅展示过程；只有高风险操作需要确认票 |
| 初稿只提到提示词塞入 200 条任务，证据不完整 | 修正为当前实际批量注入的任务、项目、想法和健康范围 |
| 项目无 Git，只有数据库备份不能保障长阶段源码回退 | 在 R0 增加本地 Git 或每阶段源码快照要求 |
| 设置页增加 token 管理可能被误认为新一轮页面扩张 | 锁定为完成“钥匙”所需的唯一设置区加法，不新增侧栏或业务页面 |

复核结论：

- 计划主线聚焦尚未完成的“钥匙”和“AI 管家”，没有重做已成型的数据库页面。
- 新增内容均服务于鉴权、工具调用、可靠性或单 EXE 交付；业务字段、统计和视觉扩张被明确延期。
- R1、R2 是 AI 写入的硬前置；R3 只读准确性是 R4 的硬门槛。
- 每个阶段都包含可判定的验收条件，高风险、重复执行、失败恢复和周期任务均有保障项。
