# Security and recovery

- The server defaults to `127.0.0.1:4738`. A non-localhost bind requires an explicit `confirm_non_localhost: true` setting update and a restart.
- The production MCP entry point is `release/Personal-AI-OS.exe --mcp`. It starts a bundled direct MCP process; the MCP layer never opens SQLite directly and calls the same validated business application as the Web UI. The development adapter (`pnpm --filter @paios/server mcp`) forwards to the local HTTP service. Both modes send `PAIOS_TOKEN` as a Bearer token, and Agent requests are validated against `api_tokens`; revoked or expired tokens are rejected and scope checks happen before handlers.
- Agent tokens are created, copied, rotated and revoked from Settings. Only a hash is persisted; the raw value is returned once.
- Agent operations cannot call confirmation approval, backup restore, archive deletion, physical deletion or settings mutation. Those are human-UI operations. The packaged `--mcp` mode is allowed to run beside the graphical workbench for ordinary use, but it still uses the same local database rules and cannot bypass the Agent boundary. It records a local ownership marker; if a restore is pending, direct MCP refuses to start or blocks requests, and the graphical workbench also refuses to apply the restore until the direct MCP process is closed.
- Write requests are recorded in `audit_logs` with a stable `change_id`, target identity and (when the target is known) before/after snapshots; request parameters and snapshots are redacted for API keys, tokens, passwords and similar secrets, then length-limited. API clients can inspect the latest 200 entries through `/api/v1/audit`.
- Ordinary Agent writes accept an idempotency key. A successful response is cached locally by key and tool name, so a timeout or transport retry cannot create a second task, finance row, account entry or other ordinary record; reusing a key for another tool is rejected.
- Agents cannot approve confirmation tickets. The Web UI is the approval surface for ideas, workflow changes, purge requests and restore requests.
- Business rows are soft-archived. Purge requests create a parked ticket and do not physically delete data.

## Backup and restore

`POST /api/v1/system/backup` checkpoints WAL and writes a consistent SQLite snapshot under the current data directory's `backups/` folder. Formal runs use `%USERPROFILE%\.paios\backups\`; development uses `.data/backups/` only when `PAIOS_DATA_DIR=.data`. Each backup category (timestamped manual copies, restore safety copies and weekly copies) keeps at most 3 verified/recent files; invalid retention settings cannot expand that limit. Separately, each startup checks the local Sunday anchor and creates one verified `weekly-YYYY-MM-DD.db` backup when that week's copy is missing.

Restore is a two-step operation: select a verified file from `GET /api/v1/system/backups`, call `POST /api/v1/system/restore`, then approve the resulting ticket in the Web UI. Approval copies the selected file to `restore.pending.db` in the same data directory; close any direct MCP process, then stop and restart the graphical workbench (or `paios serve`) to apply it. The startup path preserves the current database as a `pre-restore-*.db` backup before replacement and cleans pending WAL/SHM sidecars. A direct MCP process never consumes that pending file and blocks while it exists, so the GUI restart remains the single restore point. If the main database itself cannot be opened, close all Personal AI OS processes and run `release/Personal-AI-OS.exe --restore-latest`; this command validates and installs the newest usable backup without opening the damaged database, while preserving the old file as `corrupt-*.db`.
