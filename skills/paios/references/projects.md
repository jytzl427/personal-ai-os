# Projects

- Projects are gallery records with a separate planning workspace. Read `projects_list`, then `projects_get` before proposing a plan. `projects_get` includes a computed posture: stable maintenance, advancing, needs acceleration, blocked, stalled, learning, or paused.
- After the user confirms a stage plan covering today, you may create/update ordinary tasks in that project, change execution dates (`due_date`), split work, update the workspace, and create/update recurrence templates. The server rejects these project-advancement writes while the covering stage plan is still a draft. Recurrence instances are still generated by the server. Creating an empty project workspace is allowed before confirmation.
- Maintenance projects should be checked and repaired, not flooded with new tasks. Learning projects need a goal then study/practice/summary tasks. Build projects split into design, development, test and acceptance. Stalled or blocked projects need a cause first.
- Never set project status to `paused` or `abandoned`. Never delete, archive, restore or approve tickets.
- Idea promotion, archive, restore, purge, workflow changes and other high-risk operations require a human confirmation ticket. Stop after reporting the ticket.
